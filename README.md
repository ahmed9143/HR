# HR Enterprise — v11.2.3

نظام موارد بشرية داخلي (Python، بدون فريموورك خارجي، SQLite/PostgreSQL). هذا الملف هو نقطة الدخول الوحيدة لحالة المشروع الحالية.

## تشغيل سريع
```
pip install -r requirements.txt
python server.py
```
افتح `http://localhost:<PORT>` (البورت يظهر في الطرفية عند التشغيل). أول حساب Admin يُنشأ تلقائيًا أول مرة.

## البنية
```
server.py                  التطبيق الأساسي: تسجيل الدخول، الصلاحيات، الموظفين، الحضور، الرواتب، الـ CSS/الراوتنج
enterprise_completion.py   QR الموظفين، بطاقات الهوية، رفع صورة الموظف
v10_feature_pack.py        إضافات V10 (تُحمَّل بعد server.py)
v11_completion.py          إضافات V11
v12_enterprise.py          إضافات V12 (تصميم بطاقة الهوية، QR bulk/export)
production_ops.py          عمليات إنتاج إضافية (يُحمَّل أخيرًا)
pg_compat.py                طبقة توافق PostgreSQL الاختيارية
vendor/qrcode/              مكتبة qrcode مضمّنة محليًا (بدون اعتماد خارجي وقت التشغيل)
docs/                       أدلة نشر/بناء فعّالة (انظر تحت)
docs/archive/               تاريخ الإصدارات القديمة (V7.4 → V11.1) — مرجع فقط، غير مطلوب للتشغيل
ci/, TEST_*.py              اختبارات دخانية وقبول
DEMO_DATA/                  بيانات وهمية بالكامل لأغراض العرض/الاختبار
```

**مهم:** الملفات الخمسة `server.py → v10 → v11 → enterprise_completion → v12 → production_ops` تُحمَّل بترتيب ثابت (كل واحد يعمل monkey-patch على اللي قبله عبر `install(globals())`). لا تُغيَّر هذه المعمارية بدون اختبار كامل — أي تغيير في الترتيب يكسر الصلاحيات/الراوتات بصمت.

## آخر التعديلات (الأداء + الأمان + التنظيم)

**الأداء**
- `can()` (فحص الصلاحيات، يُستدعى ~25 مرة لكل صفحة لبناء الـ Sidebar وحده) كان يفتح اتصال SQLite جديد + 4 أوامر PRAGMA في كل استدعاء. الآن مخزّن مؤقتًا في الذاكرة لكل دور (`_ROLE_PERMS_CACHE`)، ويُفرَّغ تلقائيًا عند تعديل الصلاحيات من شاشة الأدوار. هذا كان السبب الرئيسي للبطء عند أي ضغطة.
- الـ CSS (~7.6KB) كان يُبعث inline داخل `<style>` في كل صفحة. الآن يُقدَّم كملف ثابت `/static/style.css` بترويسة `Cache-Control: public,max-age=31536000,immutable` مع نسخة (`?v=<hash>`) تتغيّر تلقائيًا عند تعديل التصميم — المتصفح يحمّله مرة واحدة فقط.
- صورة الموظف تُضغط تلقائيًا وقت الرفع (تصغير لحد أقصى 900px + JPEG جودة 85%) بدل تخزين الصورة الأصلية بحجمها الكامل وتحميلها كاملة داخل جداول الموظفين.

**الأمان**
- فحص التوقيع الحقيقي لملفات الصور (magic bytes) يشمل WEBP الآن (كان ناقصًا ويسبب كسر الرفع).
- ملفا بيانات حقيقية لـ 109 موظف (أرقام قومية، IBAN، رواتب) أُزيلا من الحزمة و`.gitignore` يستثنيهما تلقائيًا مستقبلاً. **تأكد أن هذين الملفين محفوظان خارج هذا المجلد قبل أي رفع لأي مستودع.**
- QR الموظف: تصحيح خطأ ERROR_CORRECT_H (يتحمّل ~30% تلف حتى مع شعار الشركة في المنتصف)، وترقية تلقائية لمخطط قاعدة البيانات (`qr_identities`) تضيف أي عمود ناقص (مثل `token_hash`) عند بدء التشغيل بدل الفشل الصامت على قواعد بيانات قديمة.

**التنظيم**
- حُذف الكود الميت (ملفات patch قديمة غير مستوردة، استعلام غير منفَّذ في Enterprise Center).
- التوثيق التاريخي (V7.4 → V11.1، ~22 ملف) نُقل إلى `docs/archive/` وأدلة النشر الفعّالة إلى `docs/`، بدل تكدّسها في جذر المشروع.
- اختبارات القبول تعتمد الآن على `DEMO_DATA` الوهمية بدل بيانات حقيقية.

## معروف — يحتاج قرار (لم يُنفَّذ عمدًا)
هذه تغييرات كبيرة الخطورة على نظام عليه بيانات حقيقية (رواتب/حضور)، ولا يوجد test suite سلوكي حقيقي (الاختبارات الحالية أغلبها تفحص وجود نص في الكود لا سلوكًا فعليًا). لم تُنفَّذ في هذه الجلسة لتجنّب كسر شيء بصمت:
- تقسيم `server.py` (~10,000 سطر، 217 دالة) إلى ملفات حسب الدومين — يتطلب الحفاظ الدقيق على ترتيب تحميل الإضافات أعلاه.
- تحويل الـ HTML من f-strings إلى Jinja2 (73+ بلوك، بعضها بمنطق شرطي داخل الـ f-string).
- ترحيل PostgreSQL كامل + اختبار تزامن.

إذا رغبت في البدء بأي بند، الأنسب أولاً هو إضافة اختبارات سلوكية حقيقية (تفتح صفحة فعليًا وتتحقق من محتواها) قبل أي إعادة هيكلة، حتى تُكتشف أي كسرة فورًا بدل بعد أسابيع.
